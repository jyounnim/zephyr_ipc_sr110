# Lab 01: Hello IPC — M55 → M4 Ping

SR110(sr100_rdk, Cortex-M55 + Cortex-M4 비대칭 듀얼코어) 보드에서, M55가 1초마다 보내는 신호를 M4가 받아 LED0를 토글하는 가장 단순한 형태의 코어 간 통신(IPC) 예제입니다. 이 랩은 전체 M4↔M55 IPC 커리큘럼의 출발점으로, 이후 모든 랩에서 반복해서 쓰이는 IPC의 기본 뼈대(mbox 채널 열기, 콜백 등록, ISR→워커스레드 전달)를 이 한 랩 안에서 전부 익히게 됩니다.

## 학습 목표

이 랩을 마치면 다음을 할 수 있게 됩니다.

- Zephyr의 raw `mbox` 드라이버 API(`mbox_send_dt`, `mbox_register_callback_dt`, `mbox_set_enabled_dt`)로 두 코어 사이에 최소한의 신호를 주고받는 코드를 작성할 수 있다.
- devicetree의 `mbox-consumer`(`mboxes`, `mbox-names`) 프로퍼티가 어떤 하드웨어 채널을 가리키는지 읽고 해석할 수 있다.
- mbox 수신 콜백이 **인터럽트(ISR) 컨텍스트**에서 실행된다는 사실이 왜 중요한지 설명하고, 이를 안전하게 다루는 표준 패턴(ISR → `k_msgq` → 워커 스레드)을 스스로 구현할 수 있다.
- M4/M55가 IPC용 공유 메모리 영역(`shared-memory-size`)을 어떻게 나눠 쓰는지 이해하고, 두 코어의 오버레이 설정을 정합성 있게 맞출 수 있다.
- `west build`로 M4(remote) 이미지를 먼저 빌드하고, 그 결과물을 M55(host) 이미지에 포함시켜 빌드하는 이 프로젝트의 표준 빌드 순서를 재현할 수 있다.

## 선수 지식 / 이전 랩과의 연결

Lab 01은 이 커리큘럼의 첫 번째 랩입니다. Zephyr RTOS의 기본적인 스레드/로깅 사용법(`k_thread_create`, `LOG_INF` 등)과 devicetree의 기초 개념(노드, `status`, `&label` 오버레이 문법)을 이미 알고 있다는 전제로 진행합니다. mbox나 IPC 자체에 대한 사전 지식은 필요 없습니다 — 이 랩의 핵심 목적이 바로 그 첫걸음이기 때문입니다.

이 랩에서는 **M55가 M4에게 일방적으로 신호를 보내는 한 방향** 통신만 다룹니다. M4가 M55에게 응답을 보내는 양방향 통신은 Lab 03에서 정식으로 다룹니다(다만 이 랩의 코드에도 진단 목적의 보조적인 M4→M55 회신이 이미 포함되어 있으며, 이는 뒤에서 별도로 설명합니다).

## 핵심 IPC 개념 설명

### 왜 M4와 M55는 "통신"이 필요한가

SR110은 하나의 칩 안에 성능이 높은 Cortex-M55 코어와, 저전력·실시간성에 강점이 있는 Cortex-M4 코어가 함께 들어있는 **비대칭 멀티코어(AMP, Asymmetric Multi-Processing)** SoC입니다. 두 코어는 서로 다른 Zephyr 이미지를 각자 독립적으로 부팅하고 실행합니다 — 즉 M55와 M4는 하나의 운영체제 인스턴스를 공유하는 것이 아니라, **완전히 별개의 두 대의 컴퓨터가 한 칩 안에 들어있는 것**과 같습니다.

이런 구조에서 두 코어가 서로 협력하려면(예: M55가 판단한 결과를 M4가 제어하는 LED에 반영하는 것) 함수 호출이나 전역 변수 공유 같은 단일 코어 안에서 쓰던 방법을 쓸 수 없습니다. 대신 **물리적으로 분리된 두 실행 주체 사이에 정보를 주고받는 메커니즘**, 즉 IPC(Inter-Processor Communication)가 필요합니다.

### mbox란 무엇인가 — 하드웨어 관점

`mbox`(mailbox)는 이런 프로세서 간 통신을 위해 SoC에 내장된 전용 하드웨어 블록입니다. 핵심 동작을 우체통에 비유하면 이해하기 쉽습니다.

- 한쪽 코어(예: M55)가 상대 코어에게 알릴 일이 생기면, mbox 하드웨어의 레지스터에 값을 씁니다. 이것이 "우체통에 편지를 넣는" 동작입니다.
- 이 레지스터 쓰기는 자동으로 상대 코어(M4)에 **하드웨어 인터럽트(doorbell)**를 발생시킵니다. "우체통 옆의 깃발을 세워, 편지가 왔다는 걸 알리는" 것과 같습니다.
- 인터럽트를 받은 M4는 자신의 인터럽트 서비스 루틴(ISR)에서 이를 감지하고, 필요하면 정해진 공유 메모리(shared memory) 영역에서 실제 데이터(payload)를 읽어옵니다.

즉 mbox 자체는 "인터럽트를 발생시키는 신호선"이고, 실제로 주고받는 데이터(구조체 등)는 별도로 마련된 **공유 메모리(shared memory)** 영역에 놓입니다. mbox는 "데이터가 준비됐다"는 신호(doorbell)를, 공유 메모리는 "그 데이터의 실체"를 담당하는 역할 분담입니다. 이 랩의 devicetree에 등장하는 `shared-memory-size`가 바로 그 공유 메모리 영역의 크기를 정의합니다.

### Zephyr의 mbox 드라이버 API가 추상화해주는 것

Zephyr는 이 하드웨어 메커니즘을 코어별 레지스터 주소를 직접 다루지 않고도 쓸 수 있도록 표준화된 API로 감싸줍니다(`zephyr/drivers/mbox.h`). 이 랩에서 사용하는 세 가지 핵심 함수는 다음과 같습니다.

- **`mbox_send_dt(spec, msg)`**: devicetree에 정의된 채널(`spec`)로 메시지(`msg`)를 보냅니다. 내부적으로 mbox 하드웨어 레지스터를 써서 상대 코어에 인터럽트를 발생시키고, 지정된 공유 메모리 위치에 페이로드를 씁니다.
- **`mbox_register_callback_dt(spec, callback, user_data)`**: 이 채널로 메시지가 도착했을 때 호출될 콜백 함수를 등록합니다. 이 콜백은 뒤에서 설명하듯 **ISR 컨텍스트**에서 실행됩니다.
- **`mbox_set_enabled_dt(spec, 1)`**: 등록해둔 콜백이 실제로 인터럽트에 반응하도록 채널을 활성화합니다. 콜백을 등록만 하고 이 호출을 빠뜨리면 메시지가 도착해도 아무 일도 일어나지 않습니다.

이 세 함수만으로 "보드마다 다른 mbox 하드웨어의 레지스터 배치"를 몰라도, devicetree에 선언된 채널 이름을 통해 이식성 있는 코드를 작성할 수 있습니다.

### devicetree의 `mbox-consumer` / `mboxes` 프로퍼티

mbox 채널을 코드에서 쓰려면 먼저 devicetree에 "이 애플리케이션이 어떤 mbox 채널을 쓸 것인가"를 선언해야 합니다. 이 보드의 base devicetree에는 이미 다음과 같은 형태의 `mbox-consumer` 노드가 정의되어 있습니다.

```dts
mbox_consumer: mbox-consumer {
    mboxes = <&ipc0 1>, <&ipc0 0>;
    mbox-names = "tx", "rx";
};
```

`mboxes` 프로퍼티는 `<mbox 컨트롤러, 채널 번호>` 쌍의 목록이고, `mbox-names`는 그 각각에 붙는 이름(`tx`, `rx`)입니다. 코드에서는 이 이름을 이용해 `MBOX_DT_SPEC_GET(DT_PATH(mbox_consumer), tx)`처럼 채널을 가져옵니다. 흥미로운 점은 M4와 M55에서 이 채널 번호의 tx/rx가 서로 반대로 매핑돼 있다는 것입니다 — M55가 보내는(tx) 채널이 M4에서는 받는(rx) 채널이 되는, 우체통을 마주 보고 서 있는 두 사람의 관계와 같습니다.

### 콜백이 ISR 컨텍스트에서 실행된다는 것 — 이 랩에서 가장 중요한 개념

`mbox_register_callback_dt()`로 등록한 콜백 함수는 메시지가 도착하는 즉시, **인터럽트 서비스 루틴(ISR) 컨텍스트**에서 실행됩니다. 이것은 일반적인 스레드에서 코드를 실행하는 것과는 근본적으로 다른 제약을 가집니다.

- ISR은 매우 짧고 빠르게 끝나야 합니다. 다른 인터럽트 처리를 막고, 시스템 전체의 응답성에 영향을 주기 때문입니다.
- ISR 안에서는 **블로킹(blocking) 호출을 절대 쓸 수 없습니다**. `k_msleep()`처럼 스레드를 재우는 함수는 물론이고, 뒤에 걸릴 수 있는 오래 걸리는 하드웨어 접근(예: I2C 트랜잭션)도 마찬가지입니다. ISR 안에서 블로킹 호출을 쓰면 최악의 경우 커널 전체가 멈춰버립니다.

이 랩의 M4 쪽 코드가 정확히 이 제약과 마주칩니다. M4가 제어해야 하는 LED0는 I2C로 연결된 GPIO expander(뒤에서 설명) 뒤에 있는데, I2C 트랜잭션은 본질적으로 블로킹 호출입니다. 즉 **mbox 콜백 안에서 곧바로 LED를 토글할 수 없습니다.**

이 문제를 해결하는 표준 패턴이 바로 **ISR → `k_msgq` → 워커 스레드**입니다.

1. mbox 콜백(ISR)은 도착한 메시지를 그대로 복사해 커널 메시지 큐(`k_msgq`)에 `K_NO_WAIT`로 넣기만 하고 즉시 반환합니다. 큐에 넣는 연산 자체는 논블로킹이라 ISR에서 안전합니다.
2. 별도로 만들어둔 워커 스레드가 `k_msgq_get(..., K_FOREVER)`로 큐를 기다리다가, 메시지가 들어오면 그제서야 실제로 시간이 걸리는 작업(여기서는 I2C를 통한 LED 토글)을 스레드 컨텍스트에서 안전하게 수행합니다.

이렇게 "인터럽트에서는 최소한의 일만 하고, 실제 작업은 스레드로 넘긴다"는 패턴은 이후 모든 랩에서 계속 재사용되는 이 커리큘럼의 핵심 설계 원칙입니다. 여기서 확실히 익혀두면 이후 랩들이 훨씬 수월해집니다.

## 아키텍처 / 코드 설명

### 메시지 구조체 (`lab/include/ipc_common.h`)

M55와 M4가 공통으로 이해해야 할 메시지 형식을 헤더 하나에 정의해 양쪽이 함께 include합니다.

```c
/* M55 -> M4 ping message. */
struct ipc_ping_msg {
    uint32_t seq;
};
```

`seq`는 매 전송마다 1씩 증가하는 일련번호로, "몇 번째 신호가 도착했는가"를 콘솔에서 눈으로 추적할 수 있게 해줍니다. mbox로 오가는 페이로드는 이렇게 **양쪽이 동일하게 정의한 고정 크기 struct**를 그대로 복사해서 주고받는 것이 이 커리큘럼 전체의 기본 패턴입니다.

같은 헤더에는 `struct ipc_ack_msg`도 함께 정의되어 있습니다. 이 랩은 원래 M55→M4 단방향만을 목표로 하지만, M4가 LED를 실제로 잘 토글했는지를 M55 쪽 콘솔에서도 확인할 수 있도록 자체 진단용 보조 응답 하나가 코드에 포함되어 있습니다(자세한 배경은 트러블슈팅 문서를 참고하세요). `led_ret` 필드에는 `gpio_pin_toggle_dt()`의 반환값이 그대로 담기며, `0`은 성공, 음수는 실제 에러 코드, `-1000`은 LED 디바이스 자체가 준비되지 않았음을 나타내는 값으로 사용됩니다.

### M55 (HOST) 쪽 — `lab/src/main.c`

M55는 이 랩에서 **신호를 보내는 쪽**입니다. `main()`의 흐름은 다음과 같습니다.

1. devicetree의 `mbox-consumer` 노드에서 tx/rx 채널 스펙을 가져옵니다.

   ```c
   tx_channel = (struct mbox_dt_spec)MBOX_DT_SPEC_GET(DT_PATH(mbox_consumer), tx);
   rx_channel = (struct mbox_dt_spec)MBOX_DT_SPEC_GET(DT_PATH(mbox_consumer), rx);
   ```

2. `mbox_mtu_get_dt()`로 채널의 최대 전송 크기(MTU)를 확인해, 우리가 보내려는 메시지 크기가 그 안에 들어가는지 부팅 시점에 미리 검증합니다. 이렇게 하면 메시지 크기를 잘못 잡았을 때의 오류를 실제로 전송을 시도하기 전에, 훨씬 알아보기 쉬운 형태로 잡아낼 수 있습니다.
3. 진단용 M4→M55 ack를 받기 위한 콜백을 등록·활성화합니다.
4. `while (1)` 루프에서 1초(`PING_PERIOD_MS`)마다 `seq`를 증가시키며 `mbox_send_dt()`로 M4에 ping을 보냅니다.

ack 수신 콜백(`mbox_ack_rx_callback`)은 로그만 남기는 매우 가벼운 작업이라 ISR 안에서 직접 처리해도 안전합니다 — 앞서 설명한 "ISR에서는 블로킹 금지" 원칙에 위배되지 않는, 콜백을 ISR에서 그대로 처리해도 되는 경우의 예시이기도 합니다.

### M4 (CLIENT) 쪽 — `lab/remote/src/main.c`

M4는 이 랩에서 **신호를 받아 실제 동작(LED0 토글)을 수행하는 쪽**입니다. 앞서 설명한 ISR → `k_msgq` → 워커 스레드 패턴이 그대로 구현되어 있습니다.

```c
K_MSGQ_DEFINE(rx_msgq, sizeof(struct ipc_ping_msg), 4, 4);
```

mbox 콜백은 아래처럼 큐에 넣는 일만 하고 곧바로 반환합니다.

```c
static void mbox_rx_callback(...)
{
    struct ipc_ping_msg msg = {0};
    ...
    memcpy(&msg, data->data, sizeof(msg));

    /* ISR-safe: don't touch I2C (LED) here, just enqueue */
    if (k_msgq_put(&rx_msgq, &msg, K_NO_WAIT) != 0) {
        g_msgq_drop_count++;
        ...
    }
}
```

`k_msgq_put`을 `K_NO_WAIT`로 호출하는 점에 주목하세요 — 큐가 가득 찬 경우에도 절대 대기하지 않고 즉시 실패를 반환하도록 해, ISR이 블로킹될 가능성을 원천적으로 차단합니다. 큐가 가득 차 메시지를 못 넣는 경우는 손실 카운터(`g_msgq_drop_count`)로 집계해 경고 로그를 남기되, 매번 찍지 않고 처음 한 번과 10개 단위로만 찍어 로그가 과도해지는 것을 방지합니다.

실제 LED 토글은 별도로 만든 `Toggle_Task` 워커 스레드에서 이뤄집니다.

```c
static void toggle_task_entry(void *p1, void *p2, void *p3)
{
    ...
    while (1) {
        if (k_msgq_get(&rx_msgq, &msg, K_FOREVER) != 0) {
            continue;
        }
        if (led0_ready) {
            int ret = gpio_pin_toggle_dt(&led0);
            ...
        }
        ...
    }
}
```

이 스레드는 큐에 새 메시지가 들어올 때까지 `K_FOREVER`로 잠들어 있다가, 메시지가 도착하면 깨어나 LED0를 토글합니다. `gpio_pin_toggle_dt()`는 내부적으로 I2C 트랜잭션을 수행하는, 시간이 걸리는(블로킹될 수 있는) 호출이지만, 여기는 일반 스레드 컨텍스트이므로 문제없이 안전하게 호출할 수 있습니다.

또한 `main()`에서 LED0 디바이스가 준비되지 않았더라도 그 자리에서 곧바로 함수를 종료하지 않고, `led0_ready` 플래그로 상태만 기록한 뒤 IPC 콜백 등록과 워커 스레드 생성은 그대로 진행합니다. 이렇게 하면 "LED 하드웨어에 문제가 있는 상황"과 "IPC 경로 자체가 죽어버린 상황"을 서로 다른 증상으로 명확히 구분할 수 있습니다 — 실제 시스템을 다룰 때 유용한 방어적 설계 습관입니다.

## devicetree 설정 설명

M55/M4 두 이미지는 서로 다른 devicetree를 갖고 별도로 빌드되지만, IPC로 통신하려면 몇 가지 값이 **양쪽에서 정확히 일치**해야 합니다. 그래서 각 코어의 오버레이 파일(`lab/boards/sr100_rdk_sr100_m55.overlay`, `lab/remote/boards/sr100_rdk_sr100_m4.overlay`)에 다음이 공통으로 들어갑니다.

```dts
&ipc0 {
    shared-memory-size = <0x400>;
};
```

`shared-memory-size`는 두 코어가 데이터를 주고받을 때 사용하는 공유 메모리 영역의 크기입니다. 이 값이 한쪽만 다르게 설정되면 두 이미지가 서로 다른 메모리 레이아웃을 가정하게 되어 통신이 어긋납니다. 이 랩에서 실제로 주고받는 메시지는 4바이트(`uint32_t seq` 하나)에 불과해 훨씬 작은 값으로도 충분하지만, 이후 랩들에서 더 큰 메시지를 다루게 될 것을 고려해 1KB로 미리 통일해 두었습니다.

M55 쪽 오버레이에는 이 외에도 `&i2c1`, `&gpio_exp0`, `&ov02c10`을 `status = "disabled"`로 끄는 설정이 들어 있습니다. 이는 M4와 M55가 물리적으로 같은 I2C1 버스를 공유하는 이 보드의 하드웨어 구조 때문입니다 — LED0를 실제로 구동하는 쪽은 M4이므로, M55 쪽에서는 이 버스를 아예 갖지 않도록 명시적으로 비활성화해 부팅 시 버스 소유권 충돌을 막습니다. 이 설정의 배경과 발견 경위는 트러블슈팅 문서에 자세히 정리되어 있습니다.

## 빌드 방법

이 프로젝트는 M4(remote) 이미지를 M55(host) 이미지가 참조하는 구조이므로, **반드시 M4를 먼저 빌드**해야 합니다. west 워크스페이스 루트(`zephyr/`가 보이는 디렉토리)에서 다음 순서로 진행합니다.

```bash
# 1) M4 (remote) 이미지 빌드
west build -p always -b sr100_rdk/sr100/m4 ./zephyr_ipc_sr110/01_hello_ipc/lab/remote -d m4

# 2) M55 (host) 이미지 빌드 — M4 바이너리를 포함
west build -p always -b sr100_rdk/sr100/m55 ./zephyr_ipc_sr110/01_hello_ipc/lab -d m55 \
    -DCONFIG_SR100_RELEASE_M4_RESET=y -DM4_BUILD="../m4"
```

각 플래그의 의미는 다음과 같습니다.

- `-p always`: 매번 빌드 디렉토리를 완전히 정리(pristine)하고 새로 빌드합니다. 이전 빌드의 캐시나 오버레이 설정이 남아 엉뚱한 결과가 나오는 것을 방지합니다.
- `-b <보드>/<qualifier>`: 대상 보드와 코어를 지정합니다. `sr100_rdk`가 보드명이고, `/sr100/m4`, `/sr100/m55`가 각각 M4·M55 코어를 가리키는 qualifier입니다.
- `-d <디렉토리>`: 빌드 결과물을 저장할 디렉토리를 지정합니다. M4와 M55를 서로 다른 디렉토리(`m4`, `m55`)에 나눠 빌드합니다.
- `-DCONFIG_SR100_RELEASE_M4_RESET=y`: M55 부팅 과정에서 리셋 상태로 대기 중인 M4 코어를 깨워 실행을 시작시키는 Kconfig 옵션입니다. M55가 "마스터"로서 M4를 기동시키는 이 커리큘럼의 기본 역할 분담을 반영합니다.
- `-DM4_BUILD="../m4"`: M55 빌드가 참조할 M4 빌드 결과물의 위치를 지정합니다. 이 경로는 **현재 작업 디렉토리가 아니라 M55의 빌드 디렉토리(`-d m55`로 만들어진 `m55/`) 기준 상대경로**로 해석되므로, `m4/`와 `m55/`가 형제 디렉토리인 이 구조에서는 `../m4`가 정확한 값입니다.

## 실행 및 결과 확인

두 코어는 각각 별도의 UART로 콘솔을 출력하므로, M55와 M4의 시리얼 콘솔을 각각 230400bps, 8N1 설정으로 엽니다. 정상 동작 시 다음과 같은 로그가 매초 출력됩니다.

- **M55 콘솔**: `Ping sent, seq=1`, `seq=2`, ... 형태로 매초 증가하는 ping 전송 로그가 출력되고, 곧이어 M4로부터의 진단 ack가 `[ACK] seq=N M4 alive, LED0 toggle OK` 형태로 함께 출력됩니다.
- **M4 콘솔**: `[Toggle_Task] ping seq=N -> LED0 toggle ret=0` 형태로 매초 로그가 출력되며, 동시에 보드의 LED0가 1초 간격으로 실제로 깜빡이는 것을 눈으로 확인할 수 있습니다.

보드에 이미지를 플래시하는 절차는 사용 중인 보드/툴체인의 표준 절차를 따르면 됩니다.

## 정리 / 핵심 요약

이 랩에서는 M55가 mbox로 M4에 신호를 보내고, M4가 그 신호를 받아 하드웨어(LED0)를 제어하는 가장 단순한 형태의 IPC 흐름을 구현했습니다. 핵심은 **mbox가 "데이터가 도착했다"는 신호(인터럽트)만 담당하고 실제 데이터는 devicetree로 정의된 공유 메모리를 통해 오간다는 것**, 그리고 **그 신호를 받는 콜백이 ISR 컨텍스트에서 실행되므로 블로킹 작업은 반드시 별도의 워커 스레드로 넘겨야 한다는 것**입니다. 이 ISR → `k_msgq` → 워커 스레드 패턴은 이후 등장하는 모든 랩에서 형태만 바뀌어 반복되는, 이 커리큘럼 전체를 관통하는 가장 중요한 설계 원칙입니다.
