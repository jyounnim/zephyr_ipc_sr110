# Lab 12 트러블슈팅: 전원 재연결 후 I2C "SDA Stuck Low"가 자동 복구되지 않음

## 증상

센서 모듈의 전원을 뺐다가 다시 꽂아 의도적으로 에러 상황을 만들었을 때, M55 화면과 M4
로그 모두 계속 `AHT20 ERR`/`BMP280 ERR` 상태에 머물러 있고, 자동으로 복구되지 않았습니다.

```
[00:28:03.625,000] <err> i2c_dw: SDA Stuck Low on i2c@50312000
[00:28:04.026,000] <wrn> lab12_client: AHT20 failing repeatedly -- attempting bus/sensor recovery
[00:28:04.026,000] <err> i2c_dw: SDA Stuck Low on i2c@50312000   <- 복구 시도 직후에도 재발
```

## 원인 분석

`i2c_dw: SDA Stuck Low` 로그는 이 SoC의 Synopsys DesignWare I2C 컨트롤러 드라이버
(`i2c_dw`)가 트랜잭션을 시작하기 **전에** 자체적으로 버스 상태를 점검해서 찍는 에러입니다.
이 랩이 실패 5틱마다 호출하는 `i2c_recover_bus()`가 실행된 직후에도 같은 에러가 즉시
다시 찍히는 것으로 보아, 이 호출이 실제로 버스를 풀어주는 하드웨어 복구 동작(SCL을
추가로 몇 번 클럭쳐서 SDA를 로우로 잡고 있는 슬레이브를 풀어주는 절차)을 수행하지
못하고 있는 것으로 보입니다.

`i2c_recover_bus()`가 실제 효과를 내려면 다음 조건이 필요합니다.

1. 이 SoC의 `i2c_dw` 드라이버가 `recover_bus` 콜백을 구현하고 있어야 함.
2. (일반적인 Zephyr 구현이라면) devicetree의 I2C 컨트롤러 노드에 `scl-gpios`/`sda-gpios`
   프로퍼티가 지정되어 있어, 필요할 때 해당 핀을 잠깐 일반 GPIO로 전환해 수동으로 클럭을
   만들어낼 수 있어야 함.

이 프로젝트의 `&i2c0` 오버레이에는 `scl-gpios`/`sda-gpios`가 지정되어 있지 않고, 이
SoC용 `i2c_dw` 드라이버가 이 콜백을 실제로 구현하는지도 이 환경에서는 드라이버 소스를
직접 볼 수 없어 확인하지 못했습니다.

## 현재 상태

- `lab/remote/src/main.c`의 5틱 연속 실패 시 복구 시도 로직(`i2c_recover_bus()` 호출 +
  센서 재초기화)은 그대로 남겨뒀습니다 — 이 SoC에서 `recover_bus`가 지원되거나, 전원이
  아주 짧게만 끊겼다가 버스가 저절로 안정된 경우(SDA가 실제로 stuck 상태까지 가지 않은
  경우)에는 여전히 도움이 될 수 있습니다.
- 다만 이번에 재현된 것처럼 **버스가 실제로 SDA-stuck 상태까지 간 경우**, 이 소프트웨어
  복구만으로는 풀리지 않는 것을 확인했습니다.

## 추가 조사가 필요한 부분 (다음에 시도해볼 것)

1. `zephyr_srsdk`(또는 이 SoC의 HAL) 안의 `i2c_dw` 드라이버 소스에서 `recover_bus` 콜백
   구현 여부를 직접 확인. 구현되어 있다면 어떤 devicetree 프로퍼티(`scl-gpios`/`sda-gpios`
   등)를 요구하는지 확인 후 `&i2c0` 오버레이에 추가.
2. 구현되어 있지 않다면, 소프트웨어만으로는 이 실패 모드를 해결할 수 없습니다 — 대안으로:
   - 센서 모듈 쪽에 전원 시퀀싱(예: 센서 전원 라인에 MOSFET을 달아 MCU가 제어) 회로를
     추가해, 소프트웨어가 필요 시 센서 전원을 완전히 껐다 켜서 버스를 물리적으로 리셋하는
     방법.
   - I2C 라인에 풀업저항 값을 낮춰(예: 10kΩ → 4.7kΩ 이하) 로우 상태에서도 더 빨리
     안정되도록 하는 하드웨어적 완화(다만 이미 stuck된 상태 자체를 푸는 근본 해결책은
     아님).
3. 재현 조건 좀 더 좁혀보기: 전원만 끊었다 꽂았을 때와, I2C 배선(SDA/SCL)만 끊었다 다시
   붙였을 때가 다르게 동작하는지 비교해보면 원인(슬레이브 쪽 문제 vs 컨트롤러 쪽 문제)을
   좁히는 데 도움이 될 수 있습니다.

이 SoC의 I2C 컨트롤러 드라이버가 `recover_bus`를 지원하는지에 달려 있고, 이는 드라이버
소스를 직접 봐야 확인 가능합니다.
