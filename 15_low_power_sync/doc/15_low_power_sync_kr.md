# Lab 15: Low Power Sync

## 학습 목표

- 이 SoC의 실제 설계 의도 — **M4는 Always-On으로 가벼운 센서를 상시 감시하고, M55는 평소 대기 상태로 있다가 의미 있는 이벤트가 있을 때만 깨어난다** — 를 IPC 패턴으로 직접 재현한다.
- "센서를 읽을 때마다 보낸다"(Lab 11/12/13의 주기적 전송)와 "상태가 실제로 바뀔 때만 보낸다"(이 랩)의 차이를 코드로 대비한다.
- `k_msgq_get()`을 `K_FOREVER`로 블로킹하는 것이 Lab 14의 유한 타임아웃과 어떻게 다른지, 그리고 왜 이 경우엔 `K_FOREVER`가 정답인지 이해한다.
- Zephyr의 idle 스레드가 "실행할 스레드가 없을 때" 자동으로 CPU를 저전력 대기(WFI)로 보낸다는 사실을 활용해, 별도의 전력관리 설정 없이도 "M55가 이벤트를 기다리는 동안 정말로 쉰다"는 것을 실기로 확인한다.

## 이전 랩과의 연결

Lab 15도 새 하드웨어를 전혀 추가하지 않습니다.

1. AHT20 센서(M4, I2C0) — Lab 12/13과 동일한 배선, 이번엔 AHT20만 사용(BMP280은 사용 안 함).
2. mbox 채널(`ipc0`) — 모든 랩에서 재사용.
3. M4 콘솔 UART의 폴링 커맨드 입력(Lab 13/14에서 검증된 `uart_poll_in()` 패턴) — 그대로 재사용.
4. M55의 ST7789V3 TFT(Lab 11/12/13/14와 동일한 raw-SPI 드라이버) — 그대로 재사용.

BMP280을 이번 랩에서 일부러 쓰지 않은 이유는, 이 랩의 주제가 "always-on 감시 → 이벤트 발생시에만 깨우기" 패턴 자체이지 다중 센서 처리가 아니기 때문입니다. 온도 하나만으로도 이 패턴을 충분히, 그리고 더 명확하게 보여줄 수 있습니다.

## 이 랩이 이전 랩들과 근본적으로 다른 점

Lab 11(가속도계 스트리밍), Lab 12/13(환경 센서 로깅)은 모두 "M4가 센서를 읽을 때마다(또는 일정 주기로) M55에 보낸다"는 구조였습니다. 이 방식은 값이 바뀌든 안 바뀌든 매번 mbox 메시지가 오가고, M55도 그 메시지를 계속 받아 처리해야 합니다.

이 SoC는 원래 그 반대 방향으로 설계됐습니다. M4는 저전력으로 상시 켜져 있으면서 가벼운 센서를 계속 감시하고, M55는(NPU 등 전력을 많이 쓰는 블록을 갖고 있으므로) 평소엔 할 일이 없으면 쉬다가, M4가 "이건 알려줄 만한 일이다"라고 판단했을 때만 깨어나야 합니다. Lab 15가 바로 이 구조를 처음으로 구현합니다: M4는 500ms마다 AHT20을 읽지만(이건 M4 내부에서만 일어나는 일이라 비용이 거의 없습니다), **온도가 임계값을 넘거나 다시 아래로 내려가는 순간에만** mbox로 M55에 알립니다.

## 핵심 개념

### 1. "매 샘플 전송" vs. "상태 변화시에만 전송"

```c
/* remote/src/main.c의 메인 루프 발췌 */
enum ipc15_temp_state new_state = (temp >= thresh) ? IPC15_TEMP_ABOVE : IPC15_TEMP_BELOW;

if (!have_state || new_state != current_state) {
	/* 딱 여기서만 mbox_send_dt() 호출 -- 상태가 실제로 바뀌었을 때만 */
	mbox_send_dt(&tx_channel, &mbox_msg);
	current_state = new_state;
	have_state = true;
}
```

AHT20은 500ms마다 계속 읽지만, mbox 전송은 상태가 바뀔 때만(그리고 최초 1회) 일어납니다. 온도가 임계값 근처에서 오래 머물러 있으면 몇 분이고 mbox 트래픽이 전혀 없을 수 있습니다 — 이것이 정상 동작입니다.

### 2. `K_FOREVER` vs. Lab 14의 유한 타임아웃 — 왜 다른가

Lab 14의 `Watchdog_Task`는 `k_msgq_get(&hb_msgq, &hb, K_MSEC(200))`처럼 **유한 타임아웃**을 썼습니다. 왜냐하면 그 랩은 "메시지가 안 온다"는 사실 자체를 감지해야 했기 때문입니다(침묵 = 이상 상황).

이 랩의 `Sync_Task`는 정반대입니다:

```c
if (k_msgq_get(&evt_msgq, &evt, K_FOREVER) != 0) {
	continue;
}
```

이 랩은 "메시지가 안 온다"는 사실에 아무 의미도 두지 않습니다 — 온도가 임계값을 넘지 않으면 그냥 계속 안 오는 게 정상이고, 그걸 시계로 감시할 이유가 전혀 없습니다. 그래서 `K_FOREVER`로 무기한 블로킹하는 것이 오히려 더 올바른 설계입니다. 이 두 랩을 나란히 보면 "타임아웃이 필요한 경우(부재를 감지해야 할 때)"와 "타임아웃이 불필요한 경우(존재만 감지하면 될 때)"를 구분하는 기준이 명확해집니다.

### 3. `K_FOREVER` 블로킹이 곧 저전력 대기다

Zephyr의 idle 스레드는 "지금 실행 가능한(runnable) 스레드가 하나도 없을 때" 자동으로 CPU를 WFI(Wait For Interrupt) 같은 저전력 대기 상태로 보냅니다. `Sync_Task`가 `K_FOREVER`로 블로킹돼 있고 M55에 달리 할 일이 없다면, 별도의 전력관리 Kconfig(`CONFIG_PM` 등) 없이도 M55는 이미 "이벤트가 올 때까지 쉬는" 상태에 있습니다. mbox 인터럽트가 M55를 깨우는 것 자체가 이 대기 상태에서 벗어나는 유일한 방법입니다.

**주의**: 이것은 Zephyr 커널 스케줄러 레벨의 기본 idle 동작이며, SoC의 더 깊은 저전력 모드(Suspend-to-idle, System Off 등)에 명시적으로 진입하는 것과는 다릅니다. 이 커리큘럼을 준비하는 과정에서 M55가 실제로 어떤 SoC 저전력 상태를 지원하고 `CONFIG_PM`을 켜려면 무엇이 더 필요한지는 실기로 확인되지 않았습니다. 검증되지 않은 Kconfig를 추측으로 넣는 대신, 이 랩은 **추가 설정 없이도 이미 성립하는** "idle 스레드의 자동 WFI 대기" 수준까지만 구현합니다.

### 4. 커맨드도 전부 M4-로컬 — Lab 14와 동일한 원칙

| 커맨드 | 의미 | M55로 전달? |
|---|---|---|
| `1 <celsius>` | 임계 온도를 정수 섭씨로 설정 (기본값 28C) | 아니오 (M4 로컬) |
| `2` | 현재 온도/임계값/상태/지금까지 보낸 이벤트 수 조회 | 아니오 (M4 로컬) |

임계값을 설정하거나 조회하는 것은 M4 자신의 상태를 다루는 일이라 M55와는 무관합니다. `threshold_milli_c`는 32비트 정수라서 Lab 13의 `display_mode`처럼 `atomic_t`로 충분합니다(Lab 14의 64비트 `pause_until_ms`가 `k_mutex`를 써야 했던 것과 대비됩니다).

### 5. 태그된 유니온을 다시 한번 쓰지 않는다

Lab 14와 마찬가지로, 이 랩도 mbox에 한 방향(M4→M55)으로 한 종류(`ipc15_event_payload`)의 메시지만 흘립니다. 태그가 필요 없는 이유는 Lab 14 문서와 동일합니다.

## 아키텍처 다이어그램

```
M4 (Cortex-M4, Always-On)                   M55 (Cortex-M55, 평소 idle/WFI)
──────────────────────────                   ──────────────────────────────
메인 루프 (500ms마다)                         Sync_Task
  | AHT20 읽기 (I2C0, 저비용)                  | k_msgq_get(K_FOREVER)  <- idle 스레드가
  | new_state = (temp >= thresh)               |                            여기서 WFI 진입
  |   ? ABOVE : BELOW                          |
  | new_state != current_state?                |
  |   yes -> mbox_send_dt(evt) --- mbox --->   rx_cb() -> k_msgq_put()
  |          (M55를 깨움)                       |   -> Sync_Task 깨어남
  |   no  -> mbox 전송 없음, 다음 샘플로         |   -> TFT 갱신 (TEMP/EVENTS/색상)
  | k_msleep(500ms)                            |   -> 다시 K_FOREVER로 대기

Uart_Cmd_Task                                 (M55는 명령 콘솔 없음 -- 모든 커맨드가
  | "1 N"/"2" -> handle_command()               M4 로컬이라 M55에 아무 것도 보내지 않음)
  |   (전부 M4 로컬, mbox 사용 안 함)
```

## 빌드 방법

west 워크스페이스 루트(`zephyr/`가 보이는 디렉터리)에서 실행합니다. **SR110은 M4 이미지를 먼저 빌드하고, M55를 빌드할 때 그 M4 바이너리를 `M4_BUILD`로 가져와 함께 패키징하는 순서를 반드시 지켜야 합니다** — Lab 12부터 확립된 규칙이며, 이 순서를 지키지 않으면 최종 flash 이미지에 M4 펌웨어가 아예 포함되지 않습니다.

```bash
# 1) M4 (remote) 이미지 먼저 빌드
west build -p always -b sr100_rdk/sr100/m4 ./zephyr_ipc_sr110/15_low_power_sync/lab/remote -d m4

# 2) M55 (host) 이미지 빌드 -- M4_BUILD로 위에서 만든 M4 바이너리를 가져와 함께 패키징
west build -p always -b sr100_rdk/sr100/m55 ./zephyr_ipc_sr110/15_low_power_sync/lab -d m55 \
    -DCONFIG_SR100_RELEASE_M4_RESET=y -DM4_BUILD="../m4"
```

`M4_BUILD`는 M55 빌드 디렉터리(`-d m55`) 기준 상대 경로입니다. `m4/`, `m55/`가 워크스페이스 루트 아래 형제 디렉터리인 배치라면 `../m4`가 맞습니다.

## 실행 및 결과 확인

1. M4 콘솔(J24, 230400bps)과 M55 콘솔(J14 USB-C, 115200bps)을 모두 열어둡니다.
2. 두 코어 모두 플래시 후 리셋하면, M55의 TFT에는 처음엔 회색 "WAIT"가 표시됩니다.
3. M4가 부팅 직후 첫 AHT20 판독값을 기준으로 최초 상태(ABOVE 또는 BELOW)를 M55에 전송합니다 — TFT가 즉시 초록(BELOW) 또는 빨강(ABOVE)으로 바뀌고 TEMP/EVENTS가 채워집니다.
4. M4 콘솔에 `2`를 입력해 현재 상태를 확인합니다 — `[M4] status: temp=26.500C threshold=28.000C state=BELOW events_sent=1` 형태로 출력됩니다.
5. 손으로 센서를 감싸 쥐거나 따뜻한 물체를 가까이 대서 온도를 임계값(기본 28C) 위로 올려봅니다. 온도가 임계값을 넘는 순간 M55의 TFT가 즉시 빨강 "ABOVE"로 바뀌고 EVENTS 카운트가 1 증가합니다. M4 콘솔에는 `state change: BELOW -> ABOVE @ ...` 로그가 찍힙니다.
6. 다시 식으면 임계값 아래로 내려가는 순간 TFT가 초록 "BELOW"로 바뀌고 EVENTS가 다시 1 증가합니다.
7. `1 30`처럼 임계값을 바꿔봅니다 — `[M4] threshold set to 30C (M4-local -- not sent to M55)`가 출력되고, 다음 상태 전환부터 새 임계값이 적용됩니다.
8. 온도가 임계값 근처에서 안정적으로 머무는 동안에는 M4 콘솔에 500ms마다 새 판독은 계속 찍히지만(로그 레벨에 따라), mbox 전송/M55 화면 갱신은 전혀 일어나지 않는다는 점을 확인하세요 — 이것이 이 랩의 핵심입니다.

## 정리

Lab 15는 이 SoC의 실제 설계 의도인 "M4 Always-On 감시 → M55는 의미 있는 이벤트에서만 깨어남" 패턴을 처음으로 구현했습니다. 이전 랩들의 "매 샘플/매 주기 전송"과 대비해, mbox 트래픽과 M55의 깨어나는 빈도 자체를 실제로 줄이는 설계를 코드로 확인했습니다. `k_msgq_get()`을 `K_FOREVER`로 블로킹하는 선택이 Lab 14의 유한 타임아웃과 어떻게 다른 목적을 갖는지, 그리고 이 블로킹이 Zephyr의 자동 idle/WFI 동작과 맞물려 별도 설정 없이도 "진짜로 쉬는" 대기를 만든다는 것을 실기로 확인했습니다. SoC 레벨의 명시적 저전력 모드 진입(`CONFIG_PM`)은 미검증 영역으로 남겨두었습니다.

**실기 검증 완료.** 최초 상태 전송, 임계값 상/하향 통과 시의 이벤트 전송 및 TFT 색상/EVENTS 갱신, 커맨드 `1 <celsius>`/`2`, 그리고 임계값 근처에서 안정적으로 머무는 동안 mbox 트래픽이 전혀 발생하지 않는다는 점까지 모두 실제 하드웨어에서 정상 동작함을 확인했습니다.
