# Lab 13 트러블슈팅: 콘솔 UART RX 인터럽트 미지원

## 증상

Lab 13의 커맨드 입력 기능(M4 콘솔에 `1`/`2`/`3 <0|1>`을 입력해 M55에 전달)을 실기에서 테스트했을 때, 어떤 키를 입력해도 M4 콘솔에 아무 반응이 없었습니다. 부팅 로그에는 `[Uart_Cmd_Task] started ...` 줄이 정상적으로 찍혀 있어 스레드 자체는 문제없이 떠 있었지만, 커맨드를 처리한 로그도, `unknown command` 에러도 전혀 뜨지 않았습니다.

## 진단 과정

1. **터미널 프로그램 확인**: TeraTerm은 정상적인 양방향 터미널이므로 "로그만 보여주는 뷰어라 입력이 아예 안 나간다"는 가설은 제외했습니다.
2. **Flow control 의심**: TeraTerm의 Setup → Serial port에서 Flow control이 `hardware`로 설정되어 있으면, 보드가 CTS를 assert한 적이 없을 경우 TeraTerm이 전송을 보류할 수 있다는 가설을 세우고 `none`으로 바꿔 재시도했지만 증상은 동일했습니다.
3. **진단 코드 삽입**: 다음 두 가지를 코드에 임시로 추가해 원인을 좁혔습니다.
   - `uart_irq_callback_set()`의 리턴값을 확인해 `LOG_WRN`으로 출력.
   - RX ISR이 받은 모든 바이트를 세는 원자적 카운터(`uart_isr_byte_count`)를 추가해 주기적 로그 줄에 `uart_rx_bytes=N`으로 출력.
4. **결정적 증거**: 재부팅 로그에 다음 줄이 나타났습니다.

   ```
   [00:00:00.007,000] <wrn> lab13_client: uart_irq_callback_set() returned -134 -- interrupt-driven RX may not be supported on this UART instance
   ```

   `-134`는 Zephyr 최소 libc 기준 `-ENOTSUP`입니다. 이후 `1`을 입력해도 `uart_rx_bytes`는 계속 `0`에 머물렀습니다 — 즉 바이트가 UART FIFO/드라이버 레벨에도 도달하지 못했다는 뜻이 아니라, **RX 인터럽트 콜백 자체가 이 UART 인스턴스에서 지원되지 않는다**는 것이 명확히 확인되었습니다.

## 원인

`ns16550_uart0`(M4 콘솔 UART) 인스턴스는 이 보드/SoC 조합에서 인터럽트 기반 RX(`uart_irq_callback_set()` / `uart_irq_rx_enable()`)를 지원하지 않습니다. `CONFIG_UART_INTERRUPT_DRIVEN=y`는 해당 코드 경로를 컴파일에 포함시킬 뿐, 특정 UART 인스턴스의 드라이버가 그 기능을 실제로 구현하고 있는지는 보장하지 않습니다. 지금까지 모든 랩에서 이 UART는 TX(로그 출력, 폴링 방식)로만 쓰였기 때문에 이 제약이 드러날 기회가 없었습니다.

## 해결

인터럽트 기반 설계를 포기하고, 전용 스레드(`Uart_Cmd_Task`)가 `uart_poll_in()`을 10ms 주기로 반복 호출하는 폴링 방식으로 전환했습니다. 커맨드 텍스트도 `PING`/`STATUS`/`MODE <0|1>`에서 한 자리 숫자(`1`/`2`/`3 <0|1>`)로 바꿔, 이후 유사한 문제가 생겨도 "파싱 문제인지 입력 경로 문제인지"를 더 빨리 구분할 수 있게 했습니다. 변경 후 실기에서 커맨드 왕복(M4 → M55 → M4)이 정상 동작함을 확인했습니다.

## 배운 점

- Zephyr의 인터럽트 구동 UART 관련 함수 중 일부(`uart_irq_callback_set()` 등)는 `int`를 반환하므로, 리턴값을 무시하지 말고 항상 확인해야 합니다. 반면 `uart_irq_rx_enable()`처럼 `void`를 반환하는 함수도 있어 모든 실패를 코드로 잡아낼 수 있는 것은 아니므로, 이번처럼 리턴값이 있는 함수의 결과를 실기 초기 단계에서 로그로 남겨두는 습관이 유용합니다.
- Kconfig 심볼(`CONFIG_UART_INTERRUPT_DRIVEN=y`)은 "이 기능을 쓸 수 있게 컴파일한다"는 뜻이지 "이 하드웨어에서 이 기능이 동작한다"는 보장이 아닙니다. 같은 UART 드라이버라도 인스턴스(콘솔용 vs. 범용)에 따라 지원 범위가 다를 수 있습니다.
- 인터럽트를 쓸 수 없는 상황에서는 전용 스레드의 짧은 주기 폴링이 실용적인 대안입니다. 사람이 입력하는 속도(커맨드 콘솔)처럼 마이크로초 단위 응답성이 필요 없는 경우라면 성능 손실은 무시할 만한 수준입니다.
