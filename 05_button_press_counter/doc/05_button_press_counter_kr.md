# Lab 05: 버튼 프레스 카운터 (M4 → M55)

user_button을 누를 때마다 M4가 **누적 카운트**를 계산해 mbox로 M55에 보내고, M55는 받은 값을 로그로 남기는 랩입니다.

## 학습 목표

- 반복되는 이벤트(버튼 프레스)를 매번 그대로 전달하는 대신, **누적된 상태 값(러닝 토탈)** 으로 바꿔서 코어 간에 전달하는 패턴을 이해한다.
- `zephyr,gpio-keys`의 `polling-mode` 속성이 어떤 하드웨어 제약 때문에, 그리고 어떤 devicetree 노드에 필요한지 이해한다.
- "이벤트를 세는 일"과 "이벤트에 반응하는 일"을 두 코어로 나누는 역할 분담이 왜 유용한지 설명할 수 있다.

## 이전 랩과의 연결

Lab 02(Button Pong)에서는 버튼을 누를 때마다 M4가 **시퀀스 번호(seq)** 하나를 M55로 보내고, M55는 그 이벤트가 왔다는 사실만 로그로 남겼습니다. 즉 "몇 번째 이벤트인가"는 M4가 세고 있었지만, 그 숫자 자체가 랩의 핵심 메시지는 아니었습니다.

Lab 05는 여기서 한 걸음 더 나아가, **카운트 값 자체를 메시지의 목적**으로 삼습니다. M4는 버튼이 눌릴 때마다 내부 카운터(`g_total_presses`)를 증가시키고, 그 최신 값을 그대로 M55에 실어 보냅니다. M55는 이벤트가 발생했다는 사실이 아니라 "지금까지 총 몇 번 눌렸는가"라는 **상태(state)** 를 받습니다. LED는 이번 랩에서 다루지 않습니다(Lab 02에서 이미 버튼+LED 조합을 다뤘기 때문입니다).

## 핵심 IPC 개념

### 1. 이벤트를 상태로 바꿔서 보내는 패턴

두 코어 사이에 이벤트를 전달하는 방법은 크게 두 가지로 나눌 수 있습니다.

- **이벤트 그 자체를 전달**: "지금 버튼이 눌렸다"는 사실만 보낸다. 수신 측은 자기가 직접 세거나, 매 이벤트에 반응해야 한다.
- **누적된 상태를 전달**: "지금까지 총 N번 눌렸다"는 최신 상태 값을 보낸다. 수신 측은 계산 없이 그 값을 그대로 신뢰하면 된다.

Lab 05는 후자입니다. `struct ipc_press_count_msg`는 필드가 `uint32_t total_presses` 하나뿐이며, 매 메시지가 "지금까지의 총합"을 담은 완전한 스냅샷입니다. 이 방식의 장점은 두 가지입니다.

1. **수신 측 로직이 단순해진다.** M55는 이전에 몇 번 받았는지 기억할 필요가 없습니다. 최신 메시지 하나만 보면 현재 상태를 정확히 알 수 있습니다(idempotent에 가까운 성질).
2. **메시지 유실에 어느 정도 강건하다.** 만약 mbox 메시지 하나가 어떤 이유로 씹히더라도(이 랩의 mbox HW는 기본적으로 신뢰성 있는 채널이지만, 일반적인 IPC 설계 관점에서), 다음 메시지가 오면 그 시점의 정확한 총합으로 상태가 다시 맞춰집니다. 반면 "이벤트 하나마다 +1"만 보내는 방식이었다면, 메시지 하나가 유실될 때마다 두 코어의 카운트가 영구적으로 어긋납니다.

이런 "최신 상태 스냅샷을 통째로 보낸다"는 패턴은 이후 랩들(예: 공유 카운터, 텔레메트리)에서도 반복해서 등장하는 기본 설계 원칙입니다.

### 2. `polling-mode`는 왜 부모 노드(`&buttons`)에 있어야 하는가

이 보드에서 `user_button`은 `gpio_exp0`(PCAL6416A, I2C로 연결된 GPIO 확장 칩) 뒤에 물려 있습니다. 문제는 **M4 쪽 base devicetree의 `gpio_exp0` 정의에는 `int-gpios` 프로퍼티가 없다**는 것입니다(M55 쪽 정의에는 있지만, M55는 이 랩에서 i2c1 버스 자체를 비활성화하므로 관계없습니다 — 아래 3번 참고).

`gpio_pcal64xxa.c` 드라이버는 `int-gpios`가 배선되지 않은 인스턴스에 대해서는 `pin_interrupt_configure()`가 항상 `-ENOTSUP`(-134)을 반환하도록 되어 있습니다. 즉 이 확장 칩은 애초에 인터럽트를 M4에 알려줄 물리적인 핀 연결이 없는 것입니다. 그 결과 Zephyr의 기본 `gpio-keys` 동작 방식인 "인터럽트가 오면 콜백을 호출한다"는 이 하드웨어 구성에서는 원천적으로 성립할 수 없습니다.

Zephyr는 정확히 이 상황을 위해 `zephyr,gpio-keys` 바인딩에 `polling-mode`라는 불리언 프로퍼티를 제공합니다. 이 프로퍼티를 켜면 인터럽트를 기다리는 대신, 커널 타이머가 주기적으로 핀 상태를 읽어서(기본 `debounce-interval-ms` 30ms 간격) 버튼 눌림을 감지합니다.

여기서 중요한 것은 **이 프로퍼티가 반드시 `gpio-keys` 부모 노드(`&buttons`)에 있어야 하고, 개별 버튼 자식 노드(`&user_button`)에 두면 안 된다**는 점입니다. `polling-mode`는 devicetree 바인딩(`gpio-keys.yaml`) 상 부모 노드 레벨의 프로퍼티로 선언되어 있어서, 자식 노드에 붙이면 바인딩 검증(binding validation) 에러가 납니다. 이 랩의 M4 오버레이(`lab/remote/boards/sr100_rdk_sr100_m4.overlay`)에는 다음과 같이 적용되어 있습니다.

```dts
&buttons {
	polling-mode;
};
```

### 3. M4가 폴링을 떠맡고, M55는 결과만 받는 분업 구조

폴링 모드는 CPU가 주기적으로 깨어나 핀 상태를 확인해야 하므로 인터럽트 방식보다 자원을 더 씁니다(비록 이 정도 주기의 폴링은 부담이 크지 않지만, 원칙적으로는 그렇습니다). 이 랩의 구조에서 그 부담은 전적으로 **M4**가 집니다. M4는 입력 서브시스템을 통해 버튼을 폴링하고, 눌림을 감지하고, 카운트를 올리고, mbox로 전송하는 모든 일을 담당합니다.

반면 **M55는 아무 폴링도, 아무 판단도 하지 않습니다.** M55가 하는 일은 mbox 콜백 하나를 등록해 두고, 메시지가 도착하면 그 값을 로그로 찍는 것뿐입니다. 즉 "저수준 하드웨어 폴링과 디바운싱"이라는 지저분하고 반복적인 작업은 로컬 I/O를 직접 소유한 M4가 맡고, M55는 이미 정제된 결과(현재 카운트)만 소비하는 구조입니다.

이런 역할 분담은 실제 AMP(비대칭 멀티프로세싱) 시스템에서 흔히 쓰이는 설계입니다. 저수준 센서/입력 폴링이나 실시간성이 중요한 작업은 해당 하드웨어에 물리적으로 더 가까운(또는 더 저전력인) 코어가 맡고, 상위 애플리케이션 로직이나 UI, 로깅은 다른 코어가 맡아 전체 시스템의 부하와 책임을 분산시킵니다.

## 아키텍처 및 코드 설명

### 메시지 정의 (`lab/include/ipc_common.h`)

```c
struct ipc_press_count_msg {
	uint32_t total_presses;
};
```

필드 하나짜리 단순한 구조체입니다. 이 구조체 하나가 "지금까지 총 몇 번 눌렸는가"라는 상태 전체를 표현합니다.

### M4 (CLIENT, `lab/remote/src/main.c`)

M4 쪽 구조는 세 부분으로 나뉩니다.

1. **입력 콜백 (`button_input_cb`)**: Zephyr Input 서브시스템이 버튼 눌림을 감지하면(폴링을 통해) 이 콜백이 워크큐 컨텍스트에서 호출됩니다. `INPUT_KEY_0`이면서 `value == 1`(눌림, 뗌이 아님)일 때만 메시지 큐(`press_msgq`)에 더미 바이트 하나를 넣고 즉시 반환합니다. 실제 카운트 증가나 mbox 전송은 여기서 하지 않습니다.
2. **`Send_Task` 워커 스레드 (`send_task_entry`)**: 별도 스레드에서 `press_msgq`를 블로킹 대기(`K_FOREVER`)하다가, 항목이 들어오면 `g_total_presses`를 증가시키고, 그 값을 `struct ipc_press_count_msg`에 담아 `mbox_send_dt()`로 M55에 전송합니다.
3. **`main()`**: mbox tx 채널을 초기화하고 `Send_Task` 스레드를 생성한 뒤, 나머지는 전부 이 스레드에 맡기고 자신은 잠듭니다.

입력 콜백과 실제 전송 로직을 별도 스레드로 분리한 이유는 Lab 03에서 확립된 원칙과 같습니다 — **콜백/ISR 컨텍스트에서 블로킹 호출(mbox 전송 포함)을 하지 않는다**는 것입니다. `button_input_cb`는 큐에 넣기만 하고 즉시 반환하므로 입력 서브시스템의 워크큐를 막지 않습니다. 실제로 시간이 걸릴 수 있는 mbox 전송은 전용 스레드(`Send_Task`)에서 수행됩니다.

### M55 (HOST, `lab/src/main.c`)

M55 쪽은 매우 단순합니다. `mbox_rx_callback()`을 등록하고, 메시지가 도착하면 크기를 확인한 뒤 `memcpy`로 복사해서 `total_presses` 값을 로그로 출력합니다. 이 콜백도 로그 출력만 하고 블로킹 호출이 없으므로 mbox 콜백 컨텍스트에서 바로 실행해도 안전합니다.

## devicetree 설정 설명

이 랩에는 두 개의 오버레이가 있습니다.

**`lab/boards/sr100_rdk_sr100_m55.overlay` (M55 쪽)**
- `&ipc0 { shared-memory-size = <0x400>; };` — M4/M55 두 이미지가 공유하는 IPC 메모리 영역 크기를 지정합니다. 이 값은 M4 오버레이의 동일 설정과 반드시 일치해야 합니다.
- `&i2c1 { status = "disabled"; };` — M4와 M55는 물리적으로 같은 I2C1 버스(SCL/SDA 핀)를 공유합니다. 버스 초기화 충돌을 막기 위해 M55 쪽에서는 i2c1을 비활성화하여, `gpio_exp0`(버튼이 매달린 GPIO 확장 칩)를 M4만 실제로 구동하도록 합니다.
- `&gpio_exp0 { status = "disabled"; };`, `&ov02c10 { status = "disabled"; };` — 부모 버스(i2c1)를 비활성화하는 것만으로는 부족합니다. 자식 노드는 자신의 `status`를 별도로 지정하지 않으면 기본값인 `"okay"`를 유지하기 때문에, 드라이버가 이 노드를 여전히 "활성 인스턴스"로 간주하고 컴파일에 포함시키려 합니다. 그 결과 `DT_BUS()`가 (비활성화된) i2c1 디바이스 핸들을 찾지 못해 빌드 에러가 납니다. 그래서 자식 노드들도 명시적으로 비활성화해야 합니다.

**`lab/remote/boards/sr100_rdk_sr100_m4.overlay` (M4 쪽)**
- `&ipc0 { shared-memory-size = <0x400>; };` — M55 쪽과 동일한 값.
- `&buttons { polling-mode; };` — 위 "핵심 IPC 개념" 2번에서 설명한 대로, `gpio_exp0`에 `int-gpios`가 없어 인터럽트 기반 `gpio-keys`가 동작할 수 없으므로 폴링 모드로 전환합니다.

## 빌드 방법

```bash
# 1) M4(remote) 먼저 빌드
west build -p always -b sr100_rdk/sr100/m4 ./zephyr_ipc_sr110/05_button_press_counter/lab/remote -d m4

# 2) M55(host, M4 바이너리를 M4_BUILD로 포함)
west build -p always -b sr100_rdk/sr100/m55 ./zephyr_ipc_sr110/05_button_press_counter/lab -d m55 \
    -DCONFIG_SR100_RELEASE_M4_RESET=y -DM4_BUILD="../m4"
```

> **주의**: `M4_BUILD`는 M55 빌드 디렉토리(`m55/`) 기준 상대경로입니다. `m4/`와 `m55/`가 워크스페이스 루트의 형제 디렉토리라면 `../m4`가 맞습니다.

## 실행 및 결과 확인

보드에 플래시한 뒤 시리얼 콘솔을 열면 다음과 같은 로그를 확인할 수 있습니다.

- **M4 콘솔**: 버튼을 누를 때마다 `button press #N sent to M55`가 출력되며 N이 하나씩 증가합니다. 폴링 모드로 동작하므로 `debounce-interval-ms`(기본 30ms) 정도의 지연 후에 반영됩니다.
- **M55 콘솔**: `total button presses so far: N` — M4가 보낸 최신 누적 카운트가 그대로 출력됩니다.

버튼을 여러 번 누르면서 두 콘솔의 N 값이 항상 일치하는지 확인해 보세요.

## 정리

- 매 이벤트를 그대로 전달하는 대신, **누적 상태(러닝 토탈)를 계산해서 전달**하면 수신 측 로직이 단순해지고 메시지 유실에도 더 강건해집니다.
- `zephyr,gpio-keys`의 `polling-mode`는 반드시 **부모 노드**(`&buttons`)에 적용해야 하며, 이는 이 보드의 `gpio_exp0`가 `int-gpios` 미배선으로 인터럽트 기반 버튼 입력을 지원하지 못하는 하드웨어적 제약 때문입니다.
- 저수준 폴링/디바운싱처럼 반복적이고 자원을 소모하는 작업은 하드웨어에 가까운 M4가 맡고, M55는 그 결과(카운트)만 소비하는 **역할 분담**이 AMP 구조에서 자연스러운 설계입니다.
- mbox 콜백/입력 콜백에서는 블로킹 호출을 하지 않고, 실제 전송은 별도 워커 스레드에서 처리하는 원칙(Lab 03)이 이번 랩에서도 그대로 유지됩니다.
